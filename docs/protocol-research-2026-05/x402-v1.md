# x402 v1 Research — Coinbase HTTP 402 Protocol

**Date:** 2026-05-05
**Source:** https://github.com/coinbase/x402

## Wire format

### PaymentRequirements (server response, 402)
```json
{ "scheme": "exact", "network": "base-sepolia",
  "maxAmountRequired": "1000000", "asset": "0x...USDC",
  "payTo": "0x...", "resource": "/api/foo",
  "description": "...", "mimeType": "application/json",
  "outputSchema": { ... }, "maxTimeoutSeconds": 60, "extra": { ... } }
```

### PaymentPayload (client retry, base64-encoded into `X-PAYMENT`)
```json
{ "x402Version": 2, "scheme": "exact", "network": "...",
  "payload": { "signature": "0x...",
    "authorization": { "from": "0x...", "to": "0x...",
      "value": "1000000", "validAfter": ..., "validBefore": ...,
      "nonce": "0x..." } } }
```

### Headers
- `X-PAYMENT` (request): base64-encoded `PaymentPayload`
- `X-PAYMENT-RESPONSE` (200 response): base64-encoded settlement receipt — **facilitator attestation, not a cryptographic proof**

## Settlement

- **EIP-3009 preferred, Permit2 fallback**: `assetTransferMethod` defaults to eip3009 if compatible, else permit2.
- **Single-chain per call**: `network` field pins settlement chain. CDP facilitator does NOT support cross-chain.
- **Reference facilitator**: `api.cdp.coinbase.com/x402` — centralized trust anchor.
- **Chains supported**: EVM (Base primarily) and SVM (Solana — 6 e2e tests in CDP ref impl).

## Prior art (matters for novelty)

- **z402**: Zcash extension with shielded-pool ZK proofs hiding sender/receiver/amount.
- **ChaosChain `chaoschain-x402`**: "first truly decentralized x402 facilitator with BFT consensus, replacing centralized payment verification with cryptographic proofs."
- **hozk.io**: zkVM-native facilitator producing "verifiable receipt that both client and server can trust."
- **xapi-labs `x402x-v0`**: BSC-Solana-EVM multi-VM credential routing prototype.

## Tenzro angle (MAYBE)

- **Cross-VM single-credential** (EVM + SVM + DAML/Canton via MultiVmRuntime) is technically distinctive — no x402 extension covers DAML.
- **Plonky3 settlement-AIR receipt** in `X-PAYMENT-RESPONSE`: `circuit_id="settlement"` proof replacing facilitator attestation with cryptographic finality.
- ChaosChain (BFT decentralized) and hozk.io (zkVM receipts) stake adjacent territory; Tenzro's edge is execution quality (real Plonky3 over KoalaBear, MultiVmRuntime including Canton/DAML which no x402 extension touches).

## Implementation order

1. **Spec conformance** (in progress): `crates/tenzro-payments/src/x402/mod.rs` — rename fields to match v1 wire (`PaymentRequirements`, `PaymentPayload` nested), update `X-PAYMENT` / `X-PAYMENT-RESPONSE` headers in middleware. Scope: 14-file blast radius (`tenzro-vm/src/native/mod.rs`, scheme.rs, facilitator, client, examples, integration tests). Plan: do this as a single atomic refactor in a follow-up wave; carries no novelty over stock Coinbase x402.
2. **Cross-VM extension** (DONE): `network` field accepts Tenzro VM identifiers `tenzro-evm`, `tenzro-svm`, `tenzro-daml` via `TenzroNetwork::parse()` in `crates/tenzro-payments/src/x402/receipt.rs`. `X402SettlementReceiptBody::finalized()` populates a `tenzroVm` field when settlement lands on a native Tenzro VM and omits it for external chains so stock x402 clients are unaffected. No third-party x402 extension covers DAML/Canton — this is the distinctive Tenzro angle.
3. **Plonky3 receipt** (DONE): `X-PAYMENT-RESPONSE` carries a 32-byte settlement-AIR commitment in `tenzroCommitment` (lower-case hex). The commitment binds (scheme, network, challenge_id, credential_id, resource, asset, amount, payer, recipient, tx_hash) via domain-separated SHA-256 (`tenzro/x402/receipt`) with 4-byte LE length prefixes per field — concatenation-collision resistant. `X402PaymentServer::settle` populates the receipt body in `PaymentReceipt.extra["x_payment_response"]` for transport-layer base64 encoding. Cryptographic finality comes from validators verifying the corresponding Plonky3 proof off-EVM and matching the commitment in `ZkCommitmentRegistry`. 12 unit tests cover parse + commitment determinism + collision-resistance + receipt round-trip.

## RPC surfacing

`tenzro_x402ProtocolInfo` advertises the spec, default scheme, accepted scheme registry, and the two Tenzro extensions (`cross_vm_network`, `plonky3_receipt`) with the binding-field list and verification path. Wired in `crates/tenzro-node/src/rpc.rs`; handler at `crates/tenzro-node/src/rpc_integrations.rs::handle_x402_protocol_info`.
