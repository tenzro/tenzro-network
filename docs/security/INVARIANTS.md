# Security invariants

Statements the implementation must uphold, with the code that enforces
each one. An auditor should be able to falsify an invariant by pointing
at a code path that violates it; a fuzz target listed against an
invariant exercises it mechanically (see `fuzz/README.md`).

| E9 | GPU attestation evidence comes from NVML (`libnvidia-ml.so.1`), not `libnvidia-nscq` — nscq is the NVSwitch fabric library and is the wrong dependency for single-GPU evidence. Collection fails closed on CC disabled, DevTools mode (a valid signature over a machine not enforcing confidentiality), non-production environment, no CC-capable GPU, or no CPU CVM anchor | `crates/tenzro-tee/src/nvml.rs`, `nvidia_gpu.rs` evidence path |
| E10 | An enclave response carries attestation only when the caller asked for it, and when asked the report's `user_data` is `SHA-256("tenzro/tee/enclave-response" ‖ len-prefixed(request_id, operation, data))`, binding the result to the boundary that produced it. If attestation was requested and the hardware cannot produce a report, the call fails rather than returning `attestation: None` | `crates/tenzro-tee/src/traits.rs` (`enclave_response_binding`), per-provider `execute_in_enclave` |
| E11 | A GPU attestation report with no measurement blocks is refused at parse time. It would parse and verify cleanly — the signature covers the empty record — while attesting nothing | `parse_gpu_attestation_report` |

## RPC authorization

| # | Invariant | Enforced at |
|---|---|---|
| R1 | Cross-chain mint/burn, bridge authorization, compliance (freeze/whitelist/recover), and delegation-scope mutation are admin-class: only the operator DID and the administrators the access policy names reach them | `crates/tenzro-node/src/rpc_gates.rs ADMIN_METHODS` |
| R4 | Validator gossip carries nothing a non-validator can author. There is no per-sender topic gate, so any peer may relay these topics, but a validator endpoint announcement is accepted only if it verifies under that validator's registered consensus key, and a block or certificate only under the certificate checks (C9, C10). Messages on the consensus topics are budgeted per neighbour apart from other traffic | `EndpointBook::offer` calling `EndpointAnnouncement::verify` in `crates/tenzro-consensus/src/announce.rs`; `CONSENSUS_TOPICS`, `GossipGuard` in `crates/tenzro-network/src/gossip_validation.rs` |
| R5 | Every dispatched JSON-RPC method is named in exactly one of `ADMIN_METHODS`, `OWNER_METHODS`, `OPEN_METHODS` or the reserved training names. A method in none is refused before its handler runs, so adding an RPC without deciding its gate leaves it unreachable rather than public. A test reads the dispatcher's own source and fails while any arm is unclassified — the inverse of the previous default-open allowlist, which had already produced thirteen unauthenticated methods retrofitted in the M14 wave | `crates/tenzro-node/src/rpc_gates.rs`, checked in `dispatch_request` |
| R6 | The access policy covers the service surfaces (JSON-RPC, MCP, A2A, the OpenAI-compatible API, files, the web gateway, iroh) and nothing else. `Surface` has no consensus or gossip variant, so a closed node structurally cannot stop validating. Access tokens are ES256, signed by a key derived from the node's hardware root, DPoP-bound, and re-evaluated against the policy on every request | `crates/tenzro-node/src/access.rs`, `crates/tenzro-types/src/node_access.rs` |
| W1 | A device is treated as hardware-bound only when **both** hold: the credential cannot be replicated off it (`BE=0`), and an attestation verified to a pinned vendor root says the key lives in a TEE or secure element. `BE=0` alone is a claim made by the same software making every other claim, and an unverified chain is weaker than an absent one | `device_binding::BoundDevice::is_hardware_bound`, `BindingPolicy::admit` |
| W2 | No platform account is an identity authority. A device binding rests on a signature from a key the vendor put in hardware, over a challenge we chose, verifiable against a root we pin (via the FIDO Metadata Service by AAGUID, or the platform's own root). Apple, Google and Microsoft are conduits, never authorities | `device_binding::AttestationEvidence::proves_hardware` |
| W3 | A credential reporting `BE=0` together with `BS=1` is refused before anything else is evaluated. A credential that cannot be backed up cannot be backed up, so an authenticator asserting both has disqualified its own evidence | `BindingPolicy::admit` |
| W4 | The signature counter is a clone signal only for device-bound credentials. Synced passkeys hold it at zero permanently, so counter-based clone detection built without this check locks out exactly the users whose credentials are hardest to clone | `BoundDevice::sign_count_is_meaningful` / `advance_sign_count` |
| W5 | A wallet cannot be created behind a single device. The machine the user is on is the first; a genuinely separate hardware-bound device — a phone, another machine — is required before there is anything to lose. Two credentials on one machine do not satisfy it, and a synced credential does not count toward it | `device_binding::wallet_readiness` |
| W6 | Every session names the bound device that authorised it, not only the identity. Unbinding a device ends exactly the sessions it granted and no others, so "I lost my phone" removes that phone's access while leaving the laptop in the user's hands signed in | `device_binding::revoke_sessions_for_device` |
| W7 | One node per data directory, refused before RocksDB opens. The lock lives on a file descriptor, so the kernel releases it however the process dies — a crash never leaves a stale claim that blocks the next start. The path is canonicalised, so two spellings of one directory cannot take two locks over the same bytes | `crates/tenzro-node/src/single_instance.rs`, taken in `main.rs` before `TenzroNode::new` |
| W8 | A wallet is never a precondition for operating a node privately. A wallet is required only for TNZO operations — validating, providing paid work, bonding, settlement — because it is the operator's own machine and own node, and making a wallet the price of using your own hardware would turn a sovereign tool into a custodial one. A new wallet or DID check on a non-TNZO path is a regression, not a hardening | `crates/tenzro-node/src/main.rs:504-526` (keystore unlocker optional), `crates/tenzro-node/src/rpc.rs:5583` (`settle_inference_cost` returns `NotApplicable` with no caller address), `crates/tenzro-cli/src/commands/setup.rs` (`run_local_path` / `run_private_path` carry no identity step, unlike `run_network_path`) |
