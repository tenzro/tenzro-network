# @tenzro/device-key

Hardware device keys for Node.js. The package opens a P-256 key held by this
machine's TPM 2.0 (Linux, Windows) or Apple Secure Enclave (macOS) and offers
two operations: read the public key and sign a 32-byte digest. The private key
is created inside the hardware and never leaves it: no function returns, imports or accepts private
key material, and there is no software fallback. On a machine without a TPM or
Secure Enclave, `DeviceKey.open` throws.

It is the hardware signer behind Tenzro wallets and the Tenzro SDK. The SDK's
`openHardwareSigner` and the wallet SDKs that sign on a server (a headless
wallet, a webhook signer) load it to sign with a key that stays in the chip.
A browser wallet does not use it; in a browser the same signature comes from a
passkey.

## Install

```bash
npm install @tenzro/device-key
```

The package is a small loader. The native code ships as a prebuilt binary in
one per-platform package, which npm installs by itself as an optional
dependency. Nothing is compiled and no script runs on install.

| Platform | Binary package | Hardware used |
| --- | --- | --- |
| Linux x64 (glibc) | `@tenzro/device-key-linux-x64-gnu` | TPM 2.0 at `/dev/tpmrm0` |
| Linux arm64 (glibc) | `@tenzro/device-key-linux-arm64-gnu` | TPM 2.0 at `/dev/tpmrm0` |
| macOS arm64 | `@tenzro/device-key-darwin-arm64` | Secure Enclave |
| macOS x64 | `@tenzro/device-key-darwin-x64` | Secure Enclave |
| Windows x64 | `@tenzro/device-key-win32-x64-msvc` | TPM 2.0 through TPM Base Services |

On any other platform (musl Linux, 32-bit systems, Windows on ARM) loading the
package throws an error that names the platform. Requires Node.js 18 or newer.

## Use

```js
const { createHash } = require('node:crypto');
const { DeviceKey, platformBackend } = require('@tenzro/device-key');

if (platformBackend() === null) throw new Error('no TPM or Secure Enclave here');

const key = DeviceKey.open('my-app/signing'); // created on first use
const publicKey = key.publicKey();            // 65 bytes, uncompressed SEC1

const digest = createHash('sha256').update('message').digest();
const signature = await key.signDigest(digest); // 64 bytes, r || s, low-S

```

- `platformBackend()` returns `"tpm"`, `"secure-enclave"` or `null`.
- `DeviceKey.open(label)` opens the key for a label and creates it on first
  use. The label names the key; the same label gives the same key on the same
  machine.
- `signDigest` signs a SHA-256 digest you computed; it rejects any other
  length. The result is ECDSA P-256 as raw `r || s`.
- `attest()` is declared for evidence about the key's hardware. In this
  release neither backend produces any, so it rejects with an error that says
  so. Do not rely on it to prove where a key lives.

TypeScript declarations are in `index.d.ts`.

## Requirements

- Linux: a TPM 2.0 exposed by the kernel resource manager at `/dev/tpmrm0`,
  readable and writable by the process (usually the `tss` group). The TPM must
  be provisioned once per machine (see below). A virtual TPM that the guest
  exposes at `/dev/tpmrm0` is used like a hardware one, and its trust is that
  of whoever runs the hypervisor.
- Windows: a TPM 2.0 reachable through TPM Base Services, provisioned the same
  way.
- macOS: a Secure Enclave (Apple silicon, or an Intel Mac with a T2 chip). There
  is no Secure Enclave in virtual machines.

## Provisioning a TPM

A TPM must be provisioned once before keys can be made in it: this creates the
persistent storage root, attestation key and identity key every device key
hangs from. Run it as a user that can open the TPM:

```bash
npx @tenzro/device-key provision
```

It asks before it changes the TPM (`--yes` skips the question), reports each
slot as created or already present, and is safe to repeat. It is the same
provisioning `tenzro-node tpm provision` performs, so a machine that runs a
Tenzro node needs it only once. From code, `provisionTpm()` does the same. On
a Secure Enclave there is nothing to provision. Until a TPM is provisioned,
`DeviceKey.open` fails with an error that names this command.

## Security notes

- The key is generated by the TPM or the enclave. A TPM key is a child of the
  machine's storage root, so the blob kept on disk is useless on any other
  chip. A Secure Enclave key is stored as a blob only the enclave that made it
  can use. The blobs live in `$TENZRO_DEVICE_KEY_DIR`, by default under
  `~/.local/state/tenzro/device-keys` on Linux and
  `~/Library/Application Support/Tenzro/device-keys` on macOS.
- Anyone who can open the TPM device as your user, or call the enclave as
  your process, can request signatures. The hardware protects the key from
  being copied; it does not decide which code may ask for a signature. Run
  the signing process as its own user and keep `/dev/tpmrm0` to that user.
- A signature on a Secure Enclave key may wait for user presence, so signing
  runs off the event loop and returns a promise.
- Report vulnerabilities privately to eng@tenzro.com.

## Building from source

The binding is in `sdk/tenzro-ts-sdk/native` of the
[tenzro-network](https://github.com/tenzro/tenzro-network) repository and needs
the Rust toolchain pinned there. `npm run build` compiles the binary for the
host and places it next to `index.js`, where the loader looks first.
`cargo test -p tenzro-device-key-node` tests the binding against a stand-in
signer with no hardware; `npm test` loads the real binary and checks the refusal without hardware.
The test that signs and verifies a digest creates a key in the hardware, so it
runs only with `TENZRO_DEVICE_KEY_HARDWARE_TEST=1`.
